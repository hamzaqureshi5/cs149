## 1. SPMD

**SPMD** means **Single Program, Multiple Data**.

You write **one program**. Many workers (processes or threads) all run that same program at the same time. Each worker gets a **different piece of the data**.

### Example

Add up 1,000 numbers with 4 workers:

| Worker | Adds numbers |
|---|---|
| 0 | 1 to 250 |
| 1 | 251 to 500 |
| 2 | 501 to 750 |
| 3 | 751 to 1,000 |

All four run the same code: "add up my part of the list." At the end, the 4 partial sums are combined into one total.

### How does each worker know its part?

Each worker has an ID, often called a **rank**. The program uses the rank to decide which data to use. For example: "If I am worker 2, I take items 501 to 750."

### Where you see it

- **MPI** (Message Passing Interface): used on supercomputers and clusters. The classic SPMD style.
- **GPU programming** (CUDA, OpenCL): many threads run the same function, each on different data.
- **Deep learning training**: the same model code runs on many GPUs, each with a different batch of data.

### Why people like it

- You write and keep only one program.
- It scales: add more workers to handle more data.
- It is simple to think about.

### The hard part

Workers often need to share results or wait for each other. This is done with messages or sync points (like barriers). Doing this well is the main challenge.

## 2. SPMD vs SIMD

Both run work in parallel on many pieces of data. The difference is **what is shared** and **how tightly the work is tied together**.

### SIMD: Single Instruction, Multiple Data

- One instruction is applied to many data items at the same moment.
- It happens **inside one core**, using wide registers.
- Everything moves in **lock-step**.
- Example: one "add" instruction adds 8 pairs of numbers at once.

### SPMD: Single Program, Multiple Data

- One program is run by many workers (processes or threads).
- Each worker has its **own position in the code**. They do not need to be in lock-step.
- One worker can take an `if` branch while another takes the `else` branch.
- Example: 4 MPI processes run the same code, each on its own part of a big list.

### Side by side

| | SIMD | SPMD |
|---|---|---|
| What is the same? | The instruction | The program |
| Level | Inside one core | Across many cores, threads, or machines |
| Lock-step? | Yes | No |
| Different code paths? | No | Yes |
| Typical tools | Vector instructions (AVX, SSE, NEON) | MPI, OpenMP, CUDA |

### A simple way to remember

- **SIMD**: a row of workers who all get one shouted order and do it together: "Everyone lift!"
- **SPMD**: a row of workers who all hold the same instruction book, but each reads at their own speed and may be on a different page.

### They can work together

A program can use both. For example, run many MPI processes (SPMD), and inside each one the compiler can use vector instructions (SIMD) to speed up loops.

### A note on GPUs

GPU code is *written* in SPMD style: you write one function, and many threads run it. But the hardware runs groups of threads (called warps) in a SIMD-like way. If threads in a group take different branches, the hardware has to run each branch one after the other, which is slower. This is why people sometimes call the GPU model **SIMT** (Single Instruction, Multiple Threads).

## 3. Amdahl's Law

Amdahl's Law tells you **how much faster a program can get** when you add more processors. It also shows that there is a limit.

### The basic idea

Every program has two parts:

- A part that **can** run in parallel.
- A part that **cannot** (it must run one step at a time).

More processors only speed up the parallel part. The serial part stays the same, so it sets a limit on the total speedup.

### The formula

```text
Speedup = 1 / ( S + (1 - S) / N )
```

- `S` = fraction of the program that must run serially
- `N` = number of processors
- `Speedup` = how many times faster than using 1 processor

### Example

A program takes 100 seconds on one processor. 10 seconds are serial, 90 seconds can run in parallel. So `S = 0.1`.

| Processors | Parallel part | Total time | Speedup |
|---|---|---|---|
| 1 | 90 s | 100 s | 1x |
| 10 | 9 s | 19 s | about 5.3x |
| 100 | 0.9 s | 10.9 s | about 9.2x |
| 1,000,000 | almost 0 s | about 10 s | close to 10x |

### The key lesson

The maximum speedup is `1 / S`. If 10% of your program is serial, you can never go faster than 10 times, no matter how many processors you add. Even 1% serial limits you to 100 times.

### Why it matters

- More hardware gives smaller and smaller gains.
- Making the serial part smaller often helps more than adding processors.

### A limit of the law

Amdahl's Law assumes the **problem size stays fixed**. In real life, people often use bigger machines to solve bigger problems. Then the parallel part grows while the serial part stays small. This is called **Gustafson's Law**, and it gives a more hopeful view.

## 4. Shared address space vs data parallel (overview)

These are two ways to **think about and write** parallel programs. They differ in how workers see data and how they work together.

### Shared address space model

- All workers (threads) see the **same memory**. If one worker writes a variable, the others can read it.
- Workers talk by reading and writing shared variables.
- Because many workers touch the same data, you need **locks**, **barriers**, or **atomic operations**. Without them, two workers can write the same place at the same time (a **race condition**).
- Example tools: pthreads, OpenMP, Java threads.

Picture: people working around one big whiteboard. Anyone can read or write. They must take turns.

### Data parallel model

- You describe **one operation** and say it should be applied to **every item** in a collection.
- You do not say which worker handles which item. The system decides.
- The same operation runs on all items, so there is little need for locks.
- Common shapes: map, filter, reduce.
- Example tools: `map` in functional languages, NumPy array operations, SQL, Spark, GPU libraries.

Picture: you tell a team, "Paint every fence post red." You do not say which person paints which post.

### Side by side

| | Shared address space | Data parallel |
|---|---|---|
| Main idea | Workers share memory | Same operation on every item |
| Who splits the work? | You, usually | The system, usually |
| Communication | Reading and writing shared variables | Mostly hidden inside operations like reduce |
| Locks needed? | Often | Rarely |
| Control | High | Lower |
| Ease of use | Harder, easier to make bugs | Easier, less flexible |

### Trade-offs

- Shared address space gives **more control**. You can build many kinds of parallel programs, including messy, irregular ones.
- Data parallel is **simpler and safer**, but fits best when the same work is done on many independent items.

### How they relate

They are not exclusive. A data parallel library may use threads with shared memory inside. These are ideas about the **programming model**, not the hardware.

There is also a third model, **message passing**, where workers have private memory and send messages to share data. MPI is the main example.

## 5. Pictures of both models

### Shared address space

```text
+------------------------------------------------------------+
|                       Shared memory                        |
|  [a0] [a1] [a2] [a3] [a4]  [total]  <-- shared by everyone |
+------------------------------------------------------------+
     ^            ^            ^            ^
     |            |            |            |
 [Worker 0]   [Worker 1]   [Worker 2]   [Worker 3]
```

- All workers read and write the **same memory**.
- Shared cells like `total` need **locks**, so workers take turns.

### Data parallel

```text
Input:   [item1] [item2] [item3] [item4] [item5] [item6] [item7] [item8]
            |       |       |       |       |       |       |       |
            v       v       v       v       v       v       v       v
        +--------------------------------------------------------------+
        |        Same operation on every item: "paint red"             |
        +--------------------------------------------------------------+
            |       |       |       |       |       |       |       |
            v       v       v       v       v       v       v       v
Output:  [red1]  [red2]  [red3]  [red4]  [red5]  [red6]  [red7]  [red8]
```

- You say **what to do**. The system decides **which worker takes which item**.

## 6. Example: square 8 numbers (Python)

**Task:** square every number in `[1, 2, 3, 4, 5, 6, 7, 8]`.
Answer: `[1, 4, 9, 16, 25, 36, 49, 64]`

### Way 1: Shared address space

You split the work yourself, in the main part of the program.

```python
import threading

a = [1, 2, 3, 4, 5, 6, 7, 8]
result = [0] * 8                     # shared by all workers

def worker(start, end):
    for i in range(start, end):
        result[i] = a[i] * a[i]      # write into my own spots

t0 = threading.Thread(target=worker, args=(0, 2))   # items 0-1
t1 = threading.Thread(target=worker, args=(2, 4))   # items 2-3
t2 = threading.Thread(target=worker, args=(4, 6))   # items 4-5
t3 = threading.Thread(target=worker, args=(6, 8))   # items 6-7

t0.start(); t1.start(); t2.start(); t3.start()
t0.join(); t1.join(); t2.join(); t3.join()          # wait for all

print(result)    # [1, 4, 9, 16, 25, 36, 49, 64]
```

You wrote the ranges, the threads, `start`, and `join` yourself. No lock is needed here because each worker writes to different spots.

### Way 2: Data parallel

First, a `my_map` function that is written **once**. It hides the threads.

```python
import threading

def square(x):                       # work for ONE item
    return x * x

# my own "map": apply f to every item
def my_map(f, data):
    n = len(data)
    out = [0] * n
    chunk = n // 4                   # split into 4 parts (n must divide by 4)

    def run(start, end):
        for i in range(start, end):
            out[i] = f(data[i])

    threads = []
    for k in range(4):
        t = threading.Thread(target=run, args=(k * chunk, (k + 1) * chunk))
        t.start()
        threads.append(t)
    for t in threads:
        t.join()
    return out

a = [1, 2, 3, 4, 5, 6, 7, 8]
result = my_map(square, a)           # do square for EVERY item

print(result)    # [1, 4, 9, 16, 25, 36, 49, 64]
```

The last two lines look sequential. There are no threads, ranges, or `join` in that part. The thread code moved inside `my_map`.

| | Way 1 | Way 2 |
|---|---|---|
| Where the threads are | In the main code, you see them | Inside `my_map`, hidden |
| What the main code is about | Workers and ranges | The operation (`square`) |
| Change the operation | Edit the worker | Pass a different function |

To cube numbers instead, write `def cube(x): return x * x * x` and call `my_map(cube, a)`. No thread code changes.

> **Note:** In standard Python, the Global Interpreter Lock (GIL) lets only one thread run Python code at a time. These programs show the **structure** of both models, but they will not run faster than a plain loop.

## 7. How a sum really works (reduction)

A plain sum, one worker:

```python
a = [1, 2, 3, 4, 5, 6, 7, 8]
total = 0
for x in a:
    total = total + x
print(total)   # 36
```

This takes 7 additions, one after another. Each step needs the answer from the step before, so nothing can run at the same time.

### The parallel way: add in pairs

```text
Level 0:   1    2    3    4    5    6    7    8
           \   /     \   /     \   /     \   /
Level 1:     3         7         11        15       <- 4 additions at the same time
               \     /             \     /
Level 2:         10                   26             <- 2 additions at the same time
                    \               /
Level 3:                  36                         <- 1 addition
```

- **Level 1:** 4 additions that do not depend on each other. 4 workers can do them at the same time.
- **Level 2:** 2 additions, also at the same time.
- **Level 3:** 1 last addition gives 36.

That is **3 rounds instead of 7 steps**. This kind of operation is called a **reduction**: many numbers in, one number out.

### The same idea in code (one worker, to see the levels)

```python
a = [1, 2, 3, 4, 5, 6, 7, 8]

while len(a) > 1:
    a = [a[i] + a[i + 1] for i in range(0, len(a), 2)]
    print(a)
```

Output:

```text
[3, 7, 11, 15]
[10, 26]
[36]
```

Every addition inside one level is independent. That is why a parallel system can hand them to different workers.

> **Note on NumPy:** `a.sum()` in NumPy runs in fast compiled C code, but on **one thread**. It is not a good example of work spread over many workers. The pair-tree idea is how tools that use many cores or GPUs do a reduction (for example GPU libraries, Spark, Dask).

## 8. Data parallel sum in Python

Write the work for **one pair**, then say "do this for every pair."

```python
from multiprocessing import Pool

def add_pair(pair):                 # work for ONE pair
    return pair[0] + pair[1]

if __name__ == "__main__":
    a = [1, 2, 3, 4, 5, 6, 7, 8]

    with Pool(4) as pool:
        while len(a) > 1:
            pairs = list(zip(a[0::2], a[1::2]))   # make pairs
            a = pool.map(add_pair, pairs)         # add EVERY pair at once
            print(a)
```

Output:

```text
[3, 7, 11, 15]
[10, 26]
[36]
```

| Round | Pairs | Result |
|---|---|---|
| 1 | (1,2) (3,4) (5,6) (7,8) | [3, 7, 11, 15] |
| 2 | (3,7) (11,15) | [10, 26] |
| 3 | (10,26) | [36] |

You wrote `add_pair` (knows about one pair) and a loop that makes pairs and calls `pool.map`. You did **not** write code to give parts to specific workers, a shared `total`, or a lock.

> For 8 numbers this is slower than a plain loop. Starting workers costs more than adding 8 numbers. It pays off when the list is very large.

## 9. Why is it called "data parallel"?

The parallel work comes from **the data**. You split the data into many pieces, and each piece gets the same operation at the same time.

- 8 numbers means 8 pieces of work that can run together.
- 8 million numbers means 8 million pieces.

More data means more parallel work.

### The opposite: task parallel

In **task parallel**, parallelism comes from **different jobs** running at the same time.

| | Data parallel | Task parallel |
|---|---|---|
| What is split? | The data | The jobs |
| Operation | Same on every piece | Different jobs |
| Example | Square every number in a list | One worker reads a file, one draws a chart, one sends an email |
| Work grows with | Size of the data | Number of different jobs |

Picture:

- **Data parallel:** 100 letters, 10 people each stamp 10 letters. Same job, different letters.
- **Task parallel:** 3 people do 3 different jobs: write, print, mail.

## 10. Why data parallel looks sequential

Data parallel code often **looks sequential**. That is on purpose.

```python
# looks sequential, runs one item at a time
result = [square(x) for x in a]

# looks almost the same, but the system may run items in parallel
result = my_map(square, a)
```

Both lines mean the same thing: "apply `square` to every item and give me the list of answers."

**Why it looks sequential:** you write **what** you want, not **how to run it**. You do not say "start 4 workers."

**Why it works:** each item's work does **not depend on any other item**. `square(3)` does not need the answer of `square(2)`. So the order does not matter, and the system may run items in any order, at the same time.

| Part of the code | Sequential or parallel? |
|---|---|
| The `map` call | Parallel (inside the library) |
| The code around it | Sequential, read top to bottom |
| Pair-sum rounds | Rounds go one after another, pairs inside a round run in parallel |

In **shared address space**, the code looks parallel: you can see threads, ranges, locks, and `join`.

| | Shared address space | Data parallel |
|---|---|---|
| Code looks | Parallel | Sequential |
| Parallelism is | Written by you | Hidden in the operation |

**The catch:** this only works when items are independent. If item 5 needs the answer from item 4, `map` is the wrong tool.

## 11. Same example in C++

### Way 1: Shared address space

```cpp
#include <iostream>
#include <thread>

int a[8] = {1, 2, 3, 4, 5, 6, 7, 8};
int result[8];                       // shared by all workers

void worker(int start, int end) {
    for (int i = start; i < end; i++)
        result[i] = a[i] * a[i];     // write into my own spots
}

int main() {
    std::thread t0(worker, 0, 2);    // worker 0 gets items 0-1
    std::thread t1(worker, 2, 4);    // worker 1 gets items 2-3
    std::thread t2(worker, 4, 6);    // worker 2 gets items 4-5
    std::thread t3(worker, 6, 8);    // worker 3 gets items 6-7

    t0.join(); t1.join(); t2.join(); t3.join();   // wait for all

    for (int i = 0; i < 8; i++) std::cout << result[i] << " ";
    // 1 4 9 16 25 36 49 64
}
```

### Way 2: Data parallel

```cpp
#include <iostream>
#include <thread>

int square(int x) {                  // work for ONE item
    return x * x;
}

// my own "map": apply f to every item
void my_map(int (*f)(int), int* in, int* out, int n) {
    int chunk = n / 4;               // split into 4 parts (n must divide by 4)
    std::thread t[4];
    for (int k = 0; k < 4; k++) {
        t[k] = std::thread([=]() {
            for (int i = k * chunk; i < (k + 1) * chunk; i++)
                out[i] = f(in[i]);
        });
    }
    for (int k = 0; k < 4; k++) t[k].join();
}

int main() {
    int a[8] = {1, 2, 3, 4, 5, 6, 7, 8};
    int result[8];

    my_map(square, a, result, 8);    // do square for EVERY item

    for (int i = 0; i < 8; i++) std::cout << result[i] << " ";
    // 1 4 9 16 25 36 49 64
}
```

Compile either file with:

```bash
g++ -std=c++11 -pthread file.cpp
```

`main` in Way 2 has no threads, no ranges, and no `join`. The thread code moved inside `my_map`.

## 12. `my_map` still launches threads. So what is different?

Correct: inside `my_map`, it is the same code as Way 1 (split the data, launch 4 threads, join). `my_map` is Way 1 put inside a function.

The difference is **who writes that code, and what your program depends on**.

- **Way 1:** the thread code is part of your program. Your logic and the parallel setup are mixed together.
- **Way 2:** your program only says "apply `square` to every item." The thread code belongs to `my_map`, which can be written once and replaced.

### The test: swap the inside, keep the program

Your program (the same for every version):

```python
def square(x):
    return x * x

result = my_map(square, [1, 2, 3, 4, 5, 6, 7, 8])
print(result)    # [1, 4, 9, 16, 25, 36, 49, 64]
```

Version A: no threads at all.

```python
def my_map(f, data):
    out = [0] * len(data)
    for i in range(len(data)):
        out[i] = f(data[i])
    return out
```

Version B: one thread per item.

```python
import threading

def my_map(f, data):
    out = [0] * len(data)

    def run(i):
        out[i] = f(data[i])

    threads = []
    for i in range(len(data)):
        t = threading.Thread(target=run, args=(i,))
        t.start()
        threads.append(t)
    for t in threads:
        t.join()
    return out
```

The answer is the same with the 4-thread version, version A, or version B.

In Way 1, changing from 4 workers to 8, or to no threads, means **rewriting your program**.

| | Way 1 | Way 2 |
|---|---|---|
| Thread code | In your program | Inside `my_map`, written once |
| Your program mentions threads? | Yes | No |
| Change how it runs (1 thread, 4, 100) | Rewrite your program | Replace `my_map` |

This works because `square` works on one item and touches nothing shared. The result does not depend on the order or on how many workers run.

## 13. The key difference: how workers share results

The difference shows most clearly when workers must **combine their results**.

**Task:** count how many numbers in `[1, 2, 3, 4, 5, 6, 7, 8]` are even. Answer: `4`.

### Shared address space: workers talk through a shared variable

```python
import threading

a = [1, 2, 3, 4, 5, 6, 7, 8]
count = 0                          # ONE variable, shared by all workers
lock = threading.Lock()

def worker(start, end):
    global count
    for i in range(start, end):
        if a[i] % 2 == 0:
            lock.acquire()         # take turns
            count = count + 1      # every worker updates the same variable
            lock.release()

t0 = threading.Thread(target=worker, args=(0, 4))
t1 = threading.Thread(target=worker, args=(4, 8))
t0.start(); t1.start()
t0.join(); t1.join()

print(count)    # 4
```

**Why the lock is needed.** `count = count + 1` is really three steps: read, add, write. Without the lock this can happen:

| Step | Worker 0 | Worker 1 | `count` in memory |
|---|---|---|---|
| 1 | reads `count` (0) | | 0 |
| 2 | | reads `count` (0) | 0 |
| 3 | writes 1 | | 1 |
| 4 | | writes 1 | 1 |

Two even numbers were found, but `count` is 1. One update was lost. This is a **race condition**. It depends on timing, so it may show up on some runs and not on others.

### Data parallel: workers do not talk at all

This uses the `my_map` function from section 6.

```python
def is_even(x):                    # work for ONE item, returns a value
    if x % 2 == 0:
        return 1
    return 0

flags = my_map(is_even, a)         # [0, 1, 0, 1, 0, 1, 0, 1]

count = 0
for f in flags:                    # combine step, separate from the workers
    count = count + f

print(count)    # 4
```

`is_even` never touches `count`. It takes one number and returns 0 or 1. Combining the answers is a **separate step** after all workers are done. Nothing is shared while workers run, so there is no race and no lock.

### The one difference to remember

| | Shared address space | Data parallel |
|---|---|---|
| How do workers share results? | By writing to the same variable | They don't. Each returns its own answer |
| When are answers combined? | While the workers are running | After, in a separate step |
| Why a lock? | Two workers write the same place | No shared place, so no lock |
| What a worker may do | Anything: read, write, wait, share | Only "input in, output out" per item |

### The trade

- **Shared address space** lets workers do anything with shared memory. That gives power, and it also gives race conditions.
- **Data parallel** takes that power away on purpose. A function can only turn its input into an output. In return, the system can run items in any order, on any number of workers, and the answer is always the same.

## 14. Quick summary

| Topic | One-line answer |
|---|---|
| SPMD | One program, many workers, each on different data |
| SIMD | One instruction, many data items, in lock-step inside one core |
| SPMD vs SIMD | SPMD: many workers, free paths. SIMD: one core, lock-step |
| Amdahl's Law | Max speedup is `1 / S`, where `S` is the serial fraction |
| Shared address space | Workers share memory. You manage workers and locks |
| Data parallel | Same operation on every item. System manages workers |
| Why "data parallel" | The parallel work comes from the data |
| Why it looks sequential | You write what to do, not how to run it |
| Reduction | Many values in, one value out, done as a tree of pairs |
| When data parallel fails | When items depend on each other |
| Race condition | Two workers write the same place at the same time and one update is lost |
